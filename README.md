# 找呀找——校园失物招领 WEB 应用

“找呀找”是基于第一次结对作业原型实现的校园失物招领 WEB 应用。

项目围绕以下完整流程进行开发：

**发布信息 → 首页浏览或搜索 → 查看详情 → 联系发布者 → 更新状态 → 历史记录**

项目使用原生 **HTML、CSS 和 JavaScript** 实现，不依赖服务器、数据库或第三方前端框架。

页面主要面向 PC 端横屏使用，采用简约粉色风格，并针对校园失物招领场景增加了多条件筛选、真实照片上传、历史信息归档、个人发布管理、一键复制联系方式等功能。

---

## 一、快速运行

本项目无需配置服务器环境，可直接运行。

1. 下载并解压项目；
2. 进入 `102402107-102402108` 文件夹；
3. 使用 **Google Chrome** 直接打开 `index.html`；
4. 可通过底部导航进入：
   - 首页
   - 搜索
   - 发布
   - 我的发布
5. 如需恢复初始演示数据，可点击页面右上角的 **“↻”恢复按钮**，确认后恢复示例数据。

项目支持通过 `file://` 直接运行：

- 不需要执行 `npm install`
- 不需要启动本地服务器
- 不需要连接数据库
- 不依赖网络环境

用户新发布的信息、上传的图片以及状态修改结果均保存在当前浏览器的 `localStorage` 中。

> 注意：本项目为纯前端课程作品，更换浏览器、清除浏览器数据或更换设备后，本地发布的信息不会自动同步。

## 三、已实现功能

### 1. 首页与信息浏览

首页采用 PC 横屏双栏布局。

页面左侧主要包括：

- 搜索入口
- 发布寻物启事快捷入口
- 发布招领信息快捷入口

页面右侧主要展示当前仍在进行中的失物招领信息。

首页支持：

- “全部”快速筛选
- “寻物”快速筛选
- “招领”快速筛选
- 筛选后信息数量同步变化
- 点击信息卡片进入详情页
- 信息列表区域独立滚动

首页默认只显示以下仍在进行中的信息：

- `寻找中`
- `等待认领`

已经完成的：

- `已找到`
- `已归还`

不会继续占用首页主要信息流，而是进入独立的历史记录页面。

这样可以减少已经失效的信息对真正正在寻找物品用户的干扰，提高有效信息的浏览效率。

---

### 2. 已完成信息与历史记录

首页提供“查看已完成信息”入口。

已完成页面集中展示：

- 已找到的寻物信息
- 已归还的招领信息

历史信息不会被自动删除，因此仍然可以：

- 查看原始发布内容
- 查看物品最终处理状态
- 保留完整的失物招领处理记录

通过将“进行中”和“已完成”信息进行分层，可以避免大量已经结束的信息继续占据首页主要位置。

---

### 3. 搜索与组合筛选

搜索页支持关键词搜索和多条件组合筛选。

#### 关键词搜索范围

可以根据以下内容搜索：

- 物品名称
- 物品描述
- 遗失或拾取地点
- 寻物 / 招领类型

#### 信息类型筛选

支持：

- 全部
- 寻物
- 招领

#### 物品分类

项目根据校园中常见遗失物品设置了 8 类：

1. 证件卡类
2. 数码电子
3. 学习用品
4. 生活用品
5. 衣物配饰
6. 钥匙
7. 雨具
8. 其他

#### 状态筛选

支持：

- 进行中
- 已完成
- 全部状态

#### 地点筛选

用户可以输入地点关键词，例如：

```text
图书馆
教学楼
运动场
食堂
宿舍
```

多个筛选条件可以组合使用。

例如：

```text
寻物 + 数码电子 + 图书馆 + 进行中
```

可以进一步缩小查找范围。

如果没有符合条件的信息，页面会显示明确的无结果提示，而不是出现空白页面。

在 PC 横屏模式下，仅搜索结果区域滚动，搜索框和筛选区域保持可见。

- 寻物信息

根据用户选择的类型，页面会动态调整相应文字。

### 寻物信息

- 丢失时间
- 丢失地点

### 招领信息

显示：

- 拾取时间
- 拾取地点

发布表单主要包含：

- 信息类型
- 物品名称
- 物品分类
- 时间
- 地点
- 物品描述
- 联系方式
- 真实照片（可选）

发布前会统一进行数据校验，只有填写内容符合要求后才允许发布。

## 五、表单校验

为了减少无效信息和错误信息，发布表单设置了基本校验规则。

当前主要校验内容包括：

- 必须选择寻物或招领类型
- 物品名称不能为空
- 必须选择物品分类
- 时间不能为空
- 地点不能为空
- 物品描述至少填写 5 个字
- 联系方式必须符合要求

联系方式支持：

- 11 位手机号
- 有效邮箱格式

例如：

```text
13800138000
```

或者：

```text
student@example.com
```

如果填写内容不符合要求，会在对应输入项附近显示错误提示，不会直接发布。

## 六、真实照片上传与展示

真实照片上传是本项目在基础失物招领功能之外增加的重要功能之一。

### 1. 图片数量

发布信息时：

- 可以完全不上传图片
- 可以上传 1 张图片
- 可以上传多张图片
- 最多上传 4 张图片

超过 4 张时，会提示用户图片数量超过限制，并只处理允许范围内的图片。

---

### 2. 图片大小限制

单张原始图片大小限制为：

```text
2 MB
```

如果用户选择的图片超过限制，则不会加入发布内容，并提示用户重新选择或压缩图片。

---

### 3. 图片自动压缩

为了避免手机原始照片过大导致浏览器本地存储空间不足，项目会在浏览器端对图片进行处理。

主要处理流程为：

1. 读取用户选择的图片；
2. 判断原始图片大小；
3. 将图片最长边压缩到约 900 像素；
4. 使用 Canvas 转换为 JPEG；
5. 根据图片大小逐步降低 JPEG 质量；
6. 压缩完成后再加入待发布图片列表。

这样可以明显降低图片对浏览器 `localStorage` 空间的占用。

---

### 4. 图片预览与删除

用户选择图片后，会立即显示缩略图预览。

如果选择了错误图片：

1. 将鼠标移动到图片上；
2. 图片右上角会出现删除按钮；
3. 点击删除即可移除该图片；
4. 删除后仍可以继续选择其他图片。

因此用户在正式发布前可以对照片进行检查和调整。

---

### 5. 详情页图片展示

详情页会根据用户实际上传的图片数量自动调整排版。

支持：

- 1 张图片
- 2 张图片
- 3 张图片
- 4 张图片

图片使用适应性布局，尽量让长图和宽图都能够完整显示，而不是直接裁切掉主要内容。

如果该信息没有上传真实照片，则继续显示对应的物品分类图标。

---

### 6. 大图预览

点击详情页中的任意缩略图，可以进入大图查看模式。

大图模式支持：

- 上一张
- 下一张
- 关闭按钮
- 点击遮罩区域关闭
- 按 `Esc` 键关闭
- 显示当前图片序号

这样可以在不占用详情页大量空间的情况下，让用户查看物品的更多细节。

---

## 七、详情页与联系方式

详情页主要展示以下信息：

- 寻物 / 招领类型
- 当前状态
- 物品名称
- 物品描述
- 时间
- 地点
- 物品分类
- 发布者联系方式
- 真实物品照片（如有）

对于仍在进行中的信息，用户可以复制发布者联系方式。

---

### 一键复制联系方式

详情页提供一键复制联系方式功能。

点击“复制”按钮后，会优先调用浏览器 Clipboard API。

如果当前通过 `file://` 直接打开网页，Clipboard API 因浏览器权限不可用，则自动使用兼容复制方式。

因此即使直接双击 `index.html` 打开网页，也能够尽可能保证复制功能可用。

如果自动复制失败，页面会提示用户手动复制。

---

### 已完成信息

如果信息已经被标记为：

- 已找到
- 已归还

详情页将显示完成提示：

> 这条信息已完成，无需再联系发布者。

同时不再展示联系方式复制按钮，以减少重复询问和无效联系。

## 八、“我的发布”与状态管理

“我的发布”页面用于管理当前浏览器中由用户自己发布的信息。

支持按照以下状态查看：

- 全部
- 进行中
- 已完成

用户可以点击自己发布的信息进入详情页，也可以直接进行状态管理。

---

### 1. 寻物信息状态更新

寻物信息默认状态为：

```text
寻找中
```

物品找回后可以修改为：

```text
已找到
```

即：

```text
寻找中 → 已找到
```

---

### 2. 招领信息状态更新

招领信息默认状态为：

```text
等待认领
```

物品归还后可以修改为：

```text
已归还
```

即：

```text
等待认领 → 已归还
```

---

### 3. 恢复为进行中

如果用户误操作将信息标记为完成，或者实际情况发生变化，已经完成的信息也可以恢复为进行中状态。

例如：

```text
已找到 → 寻找中
```

或者：

```text
已归还 → 等待认领
```

状态修改前会弹出确认提示，避免误操作。

状态发生变化后，会同步影响：

- 首页
- 搜索结果
- 详情页
- 我的发布
- 历史记录

---

### 4. 删除发布

如果出现以下情况：

- 发布错误
- 重复发布
- 内容填写错误
- 信息已经没有保留必要

用户可以在“我的发布”中删除对应信息。

删除前会再次确认：

> 确定删除这条发布吗？删除后无法恢复。

只有用户自己的发布提供删除操作。

非本人发布的信息只能查看和联系，不能修改状态或删除。

## 九、本地数据存储

本项目不使用服务器和数据库。

所有用户操作产生的数据均保存在当前浏览器的：

```text
localStorage
```

主要包括：

因此页面刷新后，数据仍然可以保留。

## 十、localStorage 容量保护

由于浏览器 `localStorage` 容量有限，不适合直接保存大量未经处理的原始照片。

项目采用多层保护机制：

1. 单张原始图片最大 2MB；
2. 图片最多上传 4 张；
3. 图片上传后自动缩放尺寸；
4. 自动压缩 JPEG 质量；
5. 保存数据前检查数据量；
6. 数据超过安全范围时取消本次写入并提示用户。

这样可以尽量避免出现：

> 页面显示发布成功，但刷新页面后实际数据没有成功保存

这一类问题。

## 十五、项目附加特点

在完成作业要求的基本功能后，项目还针对校园失物招领场景增加了一些便捷设计。

### 1. 真实照片上传与多图预览

用户可以为寻物或招领信息上传真实照片。

支持：

- 最多 4 张图片
- 上传前预览
- 删除错误图片
- 图片自动压缩
- 多图自适应排版
- 点击查看大图
- 上一张 / 下一张切换

真实图片可以帮助用户更直观地判断物品外观，降低仅依靠文字描述带来的误认。

---

### 2. 多条件组合筛选

除普通关键词搜索外，还支持：

- 寻物 / 招领类型
- 八类物品分类
- 地点
- 进行中 / 已完成状态

等条件组合筛选。

通过多条件筛选，可以在校园失物信息较多时快速缩小查找范围。

---

### 3. 已完成信息自动归档

如果已经完成的寻物和招领信息一直保留在首页主列表中，会增加正在寻找物品用户的浏览成本。

因此项目将：

- `已找到`
- `已归还`

的信息从首页主信息流中移出，统一进入历史记录。

既减少了无效信息干扰，也保留了完整的处理过程。

---

### 4. 一键复制联系方式

详情页提供一键复制发布者联系方式功能。

用户无需手动选中文字，只需点击复制按钮即可获得手机号或邮箱。

同时增加兼容方案，尽量保证直接通过 `file://` 打开网页时仍然能够正常使用。

---

### 5. 个人发布管理

除作业要求的状态更新外，“我的发布”还支持：

- 进行中 / 已完成筛选
- 恢复为进行中
- 删除错误发布
- 删除前二次确认

使用户能够更方便地管理自己发布的寻物和招领信息。

---

### 6. 恢复示例数据

为了方便课堂演示和重复测试，项目提供恢复示例数据功能。

用户可以一键清除当前浏览器中的操作记录，并恢复到初始演示状态。

该功能方便：

- 助教测试
- 课堂展示
- 重复走查完整流程

---

## 十六、隐私与使用范围

本项目为课程演示作品。

项目：

- 不连接服务器
- 不使用后台数据库
- 不将用户填写的信息上传到网络
- 不实现实名认证
- 不实现即时聊天
- 不实现地图定位

发布的信息、联系方式和图片仅保存在当前浏览器中。

更换浏览器、清除浏览器数据或更换设备后，数据不会自动同步。

项目内示例联系方式均为测试数据，请勿用于真实联系。

---

## 十七、项目核心流程

本项目重点完成校园失物招领的完整核心流程：

```text
发布寻物 / 招领信息
        ↓
保存到浏览器本地
        ↓
首页浏览 / 搜索筛选
        ↓
查看物品详情
        ↓
复制发布者联系方式
        ↓
线下联系发布者
        ↓
物品找回或归还
        ↓
发布者更新状态
        ↓
已完成信息进入历史记录
```

核心流程对应的主要页面为：

```text
首页
 ↓
搜索
 ↓
详情
 ↓
发布
 ↓
我的发布
 ↓
历史记录
```

## 十八、技术说明

项目主要使用以下技术：

```text
HTML5
CSS3
JavaScript
localStorage
FileReader
Canvas
Clipboard API
Node.js node:test
Node.js assert
Git
GitHub
```

其中：

- HTML 负责页面结构；
- CSS 负责横屏布局、粉色视觉风格和响应式设计；
- JavaScript 负责页面渲染、路由、搜索、筛选、发布和状态管理；
- `localStorage` 用于保存本地数据；
- FileReader 用于读取用户选择的图片；
- Canvas 用于图片尺寸与质量压缩；
- Clipboard API 用于复制联系方式；
- Node.js 内置测试工具用于核心逻辑单元测试；
- Git 与 GitHub 用于双人协作和版本管理。

## 十九、GitHub 协作方式

项目采用双人 GitHub 协作开发方式。

主要流程为：

```text
主仓库
   ↓
队友 Fork
   ↓
创建功能分支
   ↓
完成对应功能
   ↓
Commit
   ↓
Push
   ↓
Pull Request
   ↓
检查修改
   ↓
Merge 到 main
```

开发过程中按照功能进行多次提交，而不是在项目完成后一次性上传全部代码。

主要开发内容包括：

- 项目初始化
- 搜索与筛选
- 详情页与联系方式
- 寻物 / 招领发布
- 我的发布与状态更新
- PC 横屏与粉色 UI 重构
- 首页信息列表优化
- 图片上传与多图详情展示
- 最终页面与交互完善

## 二十、最终说明

“找呀找”围绕校园失物招领最核心的问题进行设计：

> 信息应该更集中、更容易寻找，也应该在物品找回后及时退出主要信息流。

因此项目没有加入复杂后台、实名认证、即时聊天、地图定位等超出本次作业范围的功能，而是重点完成并完善：

- 发布信息
- 浏览信息
- 搜索筛选
- 查看详情
- 联系发布者
- 更新状态
- 历史记录
- 个人发布管理

同时增加：

- 八类校园物品分类
- 多条件组合筛选
- 一键复制联系方式
- 真实照片上传
- 最多四图预览
- 图片自动压缩
- 图片大图查看
- 已完成信息自动归档
- 删除错误发布
- 状态恢复
- 恢复示例数据
- 浏览器本地容量保护
- PC 横屏布局优化

通过这些功能，使整个校园失物招领流程更加完整、清晰和方便使用。
