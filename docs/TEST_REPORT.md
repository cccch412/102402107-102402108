# 单元测试与人工走查报告

## 1. 测试目的

本项目为“找呀找——校园失物招领”WEB 应用。

测试的主要目的是验证项目核心业务逻辑是否能够正确处理正常情况、边界情况和异常情况，并通过人工走查进一步检查浏览器页面交互、图片上传、本地数据存储和页面布局等内容。

本次测试主要分为两部分：

1. **自动化单元测试**
   - 主要测试 `assets/js/core.js` 中可以独立验证的核心逻辑；
   - 包括搜索筛选、数据校验、信息创建、状态切换、分类处理和图片数据处理。

2. **人工测试**
   - 主要测试与浏览器 DOM、页面跳转、图片交互、`localStorage`、剪贴板和页面布局相关的功能；
   - 对自动化测试无法完整覆盖的界面交互进行补充。

通过“自动化测试 + 人工走查”相结合的方式，提高测试覆盖范围。

---

## 2. 测试工具

### 2.1 自动化测试工具

项目使用 Node.js 自带的：

```text
node:test
```

作为测试运行器，并使用：

```text
node:assert/strict
```

作为断言工具。

测试文件位于：

```text
tests/core.test.js
```

项目中的 `package.json` 配置如下：

```json
{
  "scripts": {
    "test": "node --test tests/*.test.js"
  }
}
```

因此在包含完整测试文件的本地项目根目录中执行：

```bash
npm test
```

即可运行全部自动化测试。

---

### 2.2 选择该测试工具的原因

本项目没有使用 Mocha、Jest 等第三方测试框架，而是使用 Node.js 自带的测试工具，主要原因如下：

- 不需要安装额外测试依赖；
- 测试环境配置简单；
- 适合本项目规模较小的纯 JavaScript 项目；
- 可以直接测试 `core.js` 中独立于浏览器页面的业务逻辑；
- 执行 `npm test` 即可统一运行全部测试；
- 方便开发过程中反复执行回归测试。

## 3. 单元测试简易教程

一个最基本的测试用例可以使用：

```javascript
test("测试名称", () => {
    // 调用待测试函数
    // 使用 assert 判断运行结果
});
```

例如测试文本标准化函数：

```javascript
test("01 normalize 能去除首尾空格并忽略大小写", () => {
    assert.equal(Core.normalize("  AbC "), "abc");
});
```

其中：

```javascript
test()
```

用于定义一个测试用例。

常用断言包括：

```javascript
assert.equal(实际值, 预期值);
```

用于判断两个基本值是否相等。

```javascript
assert.deepEqual(实际值, 预期值);
```

用于比较数组或对象的内容是否一致。

```javascript
assert.ok(值);
```

用于判断某个值是否为真。

本项目测试文件首先引入：

```javascript
const test = require("node:test");
const assert = require("node:assert/strict");
const Core = require("../assets/js/core.js");
```

之后即可直接测试 `core.js` 中导出的函数。

## 5. 白盒测试设计思路

本次测试采用白盒测试思路，根据 `core.js` 中函数内部的判断分支设计测试数据，使主要分支尽量至少被执行一次。

### 5.1 搜索与筛选

`filterItems()` 中存在多个判断条件：

```text
关键词
信息类型
物品分类
地点
进行中状态
已完成状态
```

因此测试时分别设计：

- 关键词命中的情况；
- 地点命中的情况；
- 寻物类型筛选；
- 分类筛选；
- 多条件组合；
- 条件冲突无结果；
- 进行中状态；
- 已完成状态；
- 状态与类型组合筛选。

这样能够验证不同判断条件是否会正确参与筛选。

---

### 5.2 表单校验

`validateItem()` 需要判断：

- 信息类型是否合法；
- 物品名称是否为空；
- 分类是否为空；
- 日期是否填写；
- 地点是否填写；
- 描述长度是否达到 5 个字；
- 联系方式是否为手机号或邮箱。

因此测试中分别设计：

- 完全空数据；
- 描述过短；
- 非法联系方式；
- 合法手机号；
- 合法邮箱。

用于覆盖校验失败和校验成功两个主要方向。

---

### 5.3 信息状态

本项目有两种业务类型：

```text
lost  → 寻物
found → 招领
```

不同类型对应不同状态。

寻物：

```text
寻找中 → 已找到
```

招领：

```text
等待认领 → 已归还
```

因此测试中分别验证：

- 新建寻物信息默认状态；
- 新建招领信息默认状态；
- 寻物状态切换；
- 寻物状态恢复；
- 招领状态切换；
- 进行中和已完成筛选。

---

### 5.4 图片数据

最终版本支持最多 4 张图片，因此在 `buildItem()` 中需要处理：

- 不上传图片；
- 上传 1 张图片；
- 上传 4 张图片；
- 上传超过 4 张图片；
- 兼容旧版单图 `image` 字段；
- 过滤非法图片数据。

因此测试数据专门覆盖图片数量的边界值：

```text
0
1
4
5
```

其中 5 张用于验证超过最大数量时是否只保留前 4 张。

## 7. 部分重要测试代码

### 7.1 关键词搜索测试

```javascript
test("02 按关键词搜索标题", () =>

```

该测试验证关键词“耳机”能否正确匹配标题中的“白色耳机”。

---

### 7.2 多条件冲突测试

```javascript
test("06 组合条件无结果时返回空数组", () =>
    assert.deepEqual(
        Core.filterItems(items, {
            type: "lost",
            category: "雨具"
        }),
        []
    )
);
```

测试数据中不存在“寻物 + 雨具”组合，因此预期结果为空数组。

该测试主要用于检查多条件同时生效时是否会错误返回其他数据。

### 7.3 非法联系方式测试

```javascript
test("09 非法联系方式会被拒绝", () => {
```

该测试输入不符合手机号或邮箱格式的联系方式：

## 8. 测试数据设计思路

测试数据不仅考虑正常使用情况，也考虑可能出现的错误输入和边界数据。

主要分为以下几类。

### 8.1 正常数据

例如：

```text
白色耳机
校园卡
图书馆
13800138000
user@example.com
```

用于验证正常情况下程序是否可以正确执行。

---

### 8.2 非法数据

例如：

```text
联系方式：123
描述：丢了
```

用于验证程序面对错误输入时是否能够拒绝数据，而不是继续创建信息。

---

### 8.3 冲突条件

例如同时要求：

```text
类型 = 寻物
分类 = 雨具
```

但测试数据中不存在对应项目。

此时程序应该返回：

```text
[]
```

而不是错误返回其他信息。

---

### 8.4 边界数据

图片数量重点测试：

```text
0 张
1 张
4 张
5 张
```

其中：

- 0 张代表最小允许数量；
- 4 张代表最大允许数量；
- 5 张代表超过限制。

这样可以验证图片数量边界是否正确。

---

### 8.5 兼容性数据

最终项目已经从早期的：

```text
image
```

单图形式扩展到：

```text
images
```

多图形式。

因此测试中特别保留旧版：

```javascript
image: "data:image/jpeg;base64,abc"
```

的场景，验证旧数据仍可以正常生成信息。

## 14. 测试总结

通过本次测试，我们更加认识到，页面“看起来能使用”并不代表程序内部逻辑一定正确。

例如：

- 搜索需要考虑关键词和多个筛选条件同时存在；
- 发布需要考虑空值和非法联系方式；
- 状态更新需要分别处理寻物和招领；
- 图片不仅要考虑正常上传，还要考虑 0 张、4 张、超过 4 张以及非法图片数据；
- 页面功能还需要考虑刷新、本地存储和直接打开 HTML 的使用方式。

因此本项目将主要业务逻辑从页面交互中拆分到 `core.js` 中，使这些函数可以独立进行单元测试。

在每轮功能开发完成后，通过：

```bash
npm test
```

重新执行自动化测试，可以及时发现已有功能是否因为新修改而受到影响。

最终结合自动化测试和 Chrome 人工走查，项目当前核心功能均能够按照预期运行。
